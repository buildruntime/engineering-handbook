# Database design

PostgreSQL is the default database for Buildruntime services. This page covers schema design and migrations. PostgreSQL-specific techniques, such as indexing and locking, are in [PostgreSQL](postgresql.md).

## Ownership

Each service owns its schema. Other services read and change that data through the service's API, never by connecting to its database. A shared database couples deployments, hides who depends on what, and makes every schema change a negotiation.

## Naming

| Object | Convention | Example |
| :-- | :-- | :-- |
| Table | Plural noun, `snake_case` | `projects`, `project_members` |
| Column | Singular, `snake_case`, no type prefix | `name`, `created_at` |
| Foreign key column | Referenced table in the singular, plus `_id` | `project_id` |
| Boolean column | A statement that is true or false | `is_public`, `has_billing` |
| Timestamp column | Past participle, plus `_at` | `created_at`, `archived_at` |
| Primary key | `pk_<table>` | `pk_projects` |
| Unique constraint | `uq_<table>_<columns>` | `uq_projects_slug` |
| Check constraint | `ck_<table>_<rule>` | `ck_projects_slug_format` |
| Foreign key | `fk_<table>_<column>_<referenced table>` | `fk_project_members_project_id_projects` |
| Index | `ix_<table>_<columns>` | `ix_projects_created_at_id` |

Constraint names matter: they appear in error messages and migrations, and code can refer to them. The SQLAlchemy naming convention in [FastAPI architecture](../backend/fastapi-architecture.md#database-models) generates exactly these names.

## Keys

- Every table has a primary key.
- Use a surrogate key that has no meaning: `uuid` when IDs are generated by the application or exposed to clients, `bigint GENERATED ALWAYS AS IDENTITY` for internal tables. Never `serial`, which is a legacy shorthand with awkward permission and ownership behaviour.
- Enforce natural keys, such as a slug or an email address, with a unique constraint as well. The surrogate key identifies the row; the unique constraint enforces the business rule.
- Index every foreign key column that is used to look up or delete rows. PostgreSQL does not create these indexes automatically. Without one, deleting a parent row scans the whole child table.

## Constraints

The database is the last line of defence for data integrity. Application code has bugs, and is not the only thing that writes to the database: migrations, scripts and manual fixes do too. Declare every rule the database can enforce:

- `NOT NULL` on every column that must have a value, which is most of them.
- `UNIQUE` for every natural key.
- `CHECK` for formats and ranges that a single row can verify.
- `FOREIGN KEY` for every reference, with an explicit `ON DELETE` behaviour.

```sql
CREATE TABLE projects (
    id          uuid         NOT NULL,
    slug        varchar(63)  NOT NULL,
    name        varchar(200) NOT NULL,
    created_at  timestamptz  NOT NULL DEFAULT now(),
    archived_at timestamptz,
    CONSTRAINT pk_projects PRIMARY KEY (id),
    CONSTRAINT uq_projects_slug UNIQUE (slug),
    CONSTRAINT ck_projects_slug_format CHECK (slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$')
);

CREATE INDEX ix_projects_created_at_id ON projects (created_at, id);

CREATE TABLE project_members (
    project_id uuid        NOT NULL,
    user_id    uuid        NOT NULL,
    role       text        NOT NULL,
    added_at   timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT pk_project_members PRIMARY KEY (project_id, user_id),
    CONSTRAINT fk_project_members_project_id_projects
        FOREIGN KEY (project_id) REFERENCES projects (id) ON DELETE CASCADE,
    CONSTRAINT ck_project_members_role CHECK (role IN ('owner', 'editor', 'viewer'))
);

-- The primary key covers lookups by project. This index covers lookups by user.
CREATE INDEX ix_project_members_user_id ON project_members (user_id);
```

A `CHECK` with a list of values is easier to change than a PostgreSQL `ENUM` type, whose values cannot be removed or reordered. Use a lookup table instead when the values carry their own data, such as a label or a sort order.

## Data types

| Data | Type | Not |
| :-- | :-- | :-- |
| Text | `text`, or `varchar(n)` where a real limit exists | `char(n)`, which pads with spaces |
| Point in time | `timestamptz` | `timestamp`, which has no time zone and is ambiguous |
| Calendar date | `date` | A timestamp at midnight |
| Money | `bigint` in minor units, or `numeric(19, 4)` | `real`, `double precision` or `money` |
| Identifier | `uuid` or `bigint` | `text` holding a UUID |
| Flag | `boolean NOT NULL DEFAULT false` | A nullable boolean, which has three states |
| Structured data with no fixed schema | `jsonb` | `json`, which keeps whitespace and duplicate keys, and cannot be indexed the same way |

`timestamptz` does not store a time zone. It stores an instant, and converts to and from the session's time zone. Keep the database and application sessions in UTC, and convert to a user's time zone only for display.

Use `jsonb` for data the service stores but does not query by its inner fields, such as a webhook payload. If you filter or join on a field inside it, make that field a column.

## Deleting data

Prefer a real `DELETE`. "Soft delete", a `deleted_at` column that every query must remember to filter, leaks deleted rows into results, breaks unique constraints, and keeps personal data that the user asked to have removed.

When the business needs a record of what existed, model that explicitly: an `archived_at` column with a meaning users understand, or an audit table that records changes. `projects.archived_at` is an example. An archived project is still a project, and the API shows it as one.

## Migrations

Schema changes are made with [Alembic](https://alembic.sqlalchemy.org/) migrations, committed with the code that needs them. Nobody changes a production schema by hand.

- Generate a migration with `alembic revision --autogenerate -m "Create projects"`, then read it. Autogenerate misses some changes, such as changes to check constraints, and gets others wrong, such as a column rename that it sees as a drop and an add.
- One migration per logical change. Never edit a migration that has run in any shared environment. Write a new one.
- Every migration has a `downgrade`, or raises an error that explains why it cannot be reversed.
- Migrations run as a separate step before the new version of the application starts (see [CI/CD](../delivery/ci-cd.md#deploying)). They must therefore work with both the old and the new version of the code. See [Zero-downtime schema changes](postgresql.md#zero-downtime-schema-changes).
- CI runs `alembic upgrade head`, then `alembic check`, which fails if the models and migrations disagree.

```python
# migrations/versions/2026_03_12_0001_create_projects.py
"""Create projects.

Revision ID: 0001
Revises:
Create Date: 2026-03-12 09:00:00
"""

from collections.abc import Sequence

import sqlalchemy as sa
from alembic import op

revision: str = "0001"
down_revision: str | None = None
branch_labels: str | Sequence[str] | None = None
depends_on: str | Sequence[str] | None = None


def upgrade() -> None:
    op.create_table(
        "projects",
        sa.Column("id", sa.Uuid(), nullable=False),
        sa.Column("slug", sa.String(length=63), nullable=False),
        sa.Column("name", sa.String(length=200), nullable=False),
        sa.Column(
            "created_at",
            sa.DateTime(timezone=True),
            server_default=sa.func.now(),
            nullable=False,
        ),
        sa.Column("archived_at", sa.DateTime(timezone=True), nullable=True),
        sa.CheckConstraint(
            "slug ~ '^[a-z0-9]+(-[a-z0-9]+)*$'", name=op.f("ck_projects_slug_format")
        ),
        sa.PrimaryKeyConstraint("id", name=op.f("pk_projects")),
        sa.UniqueConstraint("slug", name=op.f("uq_projects_slug")),
    )
    op.create_index(op.f("ix_projects_created_at_id"), "projects", ["created_at", "id"])


def downgrade() -> None:
    op.drop_index(op.f("ix_projects_created_at_id"), table_name="projects")
    op.drop_table("projects")
```

Start a new project with Alembic's async template, `alembic init -t async migrations`. Then, in `migrations/env.py`, import every module that defines models, set `target_metadata = Base.metadata`, and take the database URL from the application's settings rather than from `alembic.ini`:

```python
from app.core.config import get_settings
from app.db.base import Base
import app.projects.models  # noqa: F401  # Registers the tables on Base.metadata.

config.set_main_option("sqlalchemy.url", str(get_settings().database_url))
target_metadata = Base.metadata
```
